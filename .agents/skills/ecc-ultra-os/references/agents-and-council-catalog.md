# 🤖 Реестр 75+ специализированных ролей, Совет Четырёх (Council), GAN и Santa Method

Этот справочник содержит полный каталог специализированных инженерных ролей `ecc-ultra-os`, правила делегирования задач субагентам в Antigravity и готовые промты для запуска независимых ревьюеров без эффекта якорения (*Anti-Anchoring*).

## 📜 1. Железный Контракт Делегирования (Delegation Completion Contract)

При использовании инструментов `define_subagent` и `invoke_subagent` в Antigravity действуют 4 непреложных правила (на каждом уровне вложенности):

1. **Твой финальный ответ — это готовый результат, а не ожидание.** Никогда не завершай свой ход со словами «я запустил фоновых агентов и жду ответа», если задача требует интеграции их результатов.
2. **Кто делегировал — тот и собирает результаты.** Дождись завершения субагентов, проверь их выводы против реальной кодовой базы и синтезируй единое решение.
3. **Анти-якорение (Context Isolation для ревьюеров и Совета):** Когда запускаешь `Skeptic`, `Critic`, `Santa Reviewer` или `GAN Evaluator`, передавай им **только задачу, критерии рубрики и проверяемый артефакт/файлы** — никогда не скармливай им свои оправдания или историю того, как долго ты писал этот код.
4. **Параллелизм независимых веток:** Если нужно проверить безопасность, производительность и покрытие тестами разных модулей — запускай субагентов параллельно в одном шаге.

## 🏛️ 2. Совет Четырёх (`4-Voice Council`) — Промты для архитектурных развилок

Используй Совет Четырёх, когда у задачи есть несколько разумных архитектурных путей и важно вскрыть компромиссы до написания кода.

### Шаг 1: Сначала зафиксируй позицию `Architect` сам
Запиши в черновик свою исходную позицию, 3 сильнейших аргумента «за» и главный риск.

### Шаг 2: Запусти 3 независимых голоса (`Skeptic`, `Pragmatist`, `Critic`)
Шаблон промта для `invoke_subagent` (`TypeName: "research"`):

```text
Ты выступаешь в роли [ROLE: SKEPTIC / PRAGMATIST / CRITIC] в Совете Четырёх (4-Voice Decision Council).

Вопрос для принятия решения:
[Чёткая формулировка архитектурной или продуктовой развилки]

Контекст и ограничения проекта:
[Только факты, метрики, ключевые файлы и инварианты без навязывания мнения]

Твоя оптика анализа:
- Если ты SKEPTIC: подвергни сомнению саму постановку задачи, найди ложные допущения, предложи альтернативу, которая в 3 раза проще или не требует нового кода вообще.
- Если ты PRAGMATIST: оптимизируй под скорость поставки (Time-to-Market), простоту поддержки, минимум внешних зависимостей и предсказуемость в продакшене.
- Если ты CRITIC: ищи краевые случаи, состояния гонки (race conditions), отказы сети/БД, уязвимости безопасности, проблемы миграции и причины, почему этот план провалится под нагрузкой.

Ответь строго в формате (до 250 слов, без воды):
1. Позиция (1–2 предложения): какой путь выбрать и почему.
2. Аргументы (3 плотных пункта).
3. Главный риск (1 пункт): что может пойти не так в твоём варианте.
4. Слепое пятно (1 пункт): что наверняка упустят остальные участники Совета.
```

### Шаг 3: Синтез вердикта Совета
Выведи пользователю:
- Позиции всех 4 голосов (`Architect`, `Skeptic`, `Pragmatist`, `Critic`);
- **Consensus (В чём сошлись)**;
- **Strongest Dissent (Самое сильное несогласие и почему оно учтено или отклонено)**;
- **Premise Check (Удалось ли Скептику упростить саму задачу?)**;
- **Final Recommendation (Итоговый план действий)**.

## 🎅 3. Двойная слепая приёмка (`Santa Method` — Dual Adversarial Review)

Один агент, проверяющий свой же код, разделяет те же слепые пятна, которые породили баг. В методе Санты запускаются **два независимых ревьюера (`Reviewer A` и `Reviewer B`)**, которые не видят отчётов друг друга. Итоговый статус `NICE (PASS)` присваивается **только если оба вернули `PASS`**.

### Промт для `Santa Reviewer A` (Функциональная полнота, Типы, Архитектура, Краевые случаи):
```text
Ты — Независимый Инженерный Ревизор A (Santa Method — Architecture, Types & Edge Cases).
Ты НЕ видел других ревью этого кода. Твоя задача — найти реальные дефекты, а не похвалить автора.

Исходное требование (Spec):
[Текст задачи / критерии приёмки]

Проверяемые файлы / git diff:
[Список изменённых файлов]

Проверь код строго по рубрике (PASS / FAIL по каждому пункту):
1. Completeness: все ли требования спецификации реализованы от начала до конца без заглушек и TODO?
2. Type Safety & Invariants: нет ли утечек `any`, небезопасных кастов (`as unknown as X`), необработанных `null`/`undefined`?
3. Edge Cases & Concurrency: что произойдёт при пустых входах, огромных массивах, таймаутах, повторных вызовах (idempotency) и гонках состояний?
4. Silent Failures: нет ли проглоченных ошибок в `catch` или тихих дефолтов, маскирующих сбои?
5. Code Hygiene & Immutability: соблюдена ли иммутабельность, нет ли дублирования существующих утилит проекта?

Верни структурированный вердикт:
- VERDICT: PASS или FAIL
- CRITICAL_ISSUES: точный список блокеров с указанием файла, строки и способа исправления
- NON_BLOCKING_SUGGESTIONS: мелкие улучшения
```

### Промт для `Santa Reviewer B` (Безопасность, Надёжность, БД и Производительность):
```text
Ты — Независимый Ревизор Безопасности и Надёжности B (Santa Method — AppSec, Data Integrity & Performance).
Ты НЕ видел других ревью этого кода. Твоя задача — сломать защиту и найти узкие места.

Исходное требование (Spec):
[Текст задачи]

Проверяемые файлы / git diff:
[Список изменённых файлов]

Проверь код строго по рубрике (PASS / FAIL по каждому пункту):
1. Input Validation & Injection Defense: валидируются ли все входы на границе системы (Zod/Pydantic)? Нет ли SQLi, NoSQLi, XSS, Command Injection, Path Traversal, SSRF?
2. AuthN / AuthZ & IDOR: проверены ли права доступа к ресурсу на сервере (не только в UI)? Нельзя ли подменить чужой ID?
3. Secrets & Data Exposure: нет ли захардкоженных ключей/токенов и не утекают ли внутренние стектрейсы/ПДн в ответах API?
4. Database & Transactions: атомарны ли многошаговые записи (транзакции), нет ли проблемы N+1 запросов, есть ли нужные индексы?
5. Resource & Config Integrity: закрываются ли соединения/стримы/таймеры, не были ли ослаблены правила линтера или tsconfig?

Верни структурированный вердикт:
- VERDICT: PASS или FAIL
- CRITICAL_ISSUES: точный список блокеров с указанием файла, строки и способа исправления
- NON_BLOCKING_SUGGESTIONS: рекомендации по усилению
```

## 🎨 4. Состязательный контур `GAN-Style Harness` (Planner $\rightarrow$ Generator $\leftrightarrow$ Evaluator)

Используется при разработке полноценных приложений, дашбордов и сложных пользовательских интерфейсов, где недопустима «шаблонная ИИ-эстетика» (*AI slop*).

### Матрица оценки `GAN Evaluator` (Порог прохождения: $\ge 8.5 / 10$, минимум по любой оси: $8.0$):

| Ось оценки | Вес | 1–4 балла (AI Slop / Брак) | 5–7 баллов (Средне) | 8–10 баллов (Production Craft) |
| :--- | :---: | :--- | :--- | :--- |
| **1. Design Quality** | `0.20` | Шаблонные цвета, кривые отступы, визуальный шум | Чисто, но безлико и стандартно | Выверенная дизайн-система, глубина, контраст, характер |
| **2. Originality & Taste** | `0.15` | Базовый Bootstrap/Tailwind-шаблон без идеи | Стандартные паттерны с мелкими правками | Осознанное стилевое направление, продуманные акценты |
| **3. UI/UX Craft & A11y** | `0.15` | Ломается на мобильных, нет `loading`/`error`/`empty`, нет фокуса | Работает десктоп, базовые состояния | Идеальный адаптив (`375px`–`1440px`), клавиатурная навигация, микро-анимации |
| **4. Functionality** | `0.25` | Кнопки-пустышки, фейковые данные, падения на краях | Работает только Happy Path | Все сценарии, фильтрация, формы, БД и ошибки работают безотказно |
| **5. Security & Types** | `0.15` | `any`, нет серверной валидации, дыры в доступах | Частичная типизация и валидация | `0` ошибок `tsc`, полная валидация схем, защита ролей и сессий |
| **6. Performance** | `0.10` | Лаги рендера, $N+1$ запросов, огромные бандлы | Приемлемо на малых данных | Мемоизация, пагинация/виртуализация, быстрые запросы и индексы |

## 🗂️ 5. Полный каталог 75+ специализированных ролей ECC Ultra OS

В зависимости от задачи агент автоматически активирует нужную экспертную оптику (или делегирует задачу профильному субагенту):

### A. Ядро инженерии и Архитектуры (Core Engineering & Architecture)
1. **`planner`** — декомпозиция эпиков в тонкие вертикальные срезы (`task_list`) с оценкой рисков.
2. **`blueprint-architect`** — генерация многошаговых планов (`Blueprint`) с Cold-Start брифами для каждого PR.
3. **`ralphinho-dag-orchestrator`** — разбиение крупных RFC на ориентированный граф независимых юнитов (`DAG`) с очередью слияния (`Merge Queue`).
4. **`architect`** — высокоуровневый системный дизайн (C4, модульные границы, масштабируемость, отказоустойчивость).
5. **`code-architect`** — проектирование новых фич с полным сохранением идиоматики и конвенций существующего репозитория.
6. **`spec-miner`** — реверс-инжиниринг спецификаций и скрытых контрактов из легаси/brownfield-проектов.
7. **`code-explorer`** — глубокая трассировка путей выполнения (`Execution Path Tracing`) и графов вызовов.
8. **`type-design-analyzer`** — проектирование строгих типов, брендированных примитивов (`Branded Types`), дискриминированных объединений (`Discriminated Unions`) и инвариантов.
9. **`api-architect`** — проектирование контрактов REST / OpenAPI 3.1 / GraphQL / gRPC, идемпотентности, пагинации и версионирования.
10. **`database-reviewer`** — проектирование схем PostgreSQL / MySQL / SQLite / BigQuery, нормализация, индексы, партиционирование, RLS и транзакции.

### B. Качество кода, Тестирование и Надёжность (Quality, TDD & Reliability)
11. **`tdd-guide`** — ведение цикла `RED -> GREEN -> REFACTOR`, проверка покрытия $\ge 80\%$ и генерация отчёта `TDD Evidence Report`.
12. **`code-reviewer`** — комплексный аудит читаемости, модульности, иммутабельности и поддерживаемости кода.
13. **`silent-failure-hunter`** — специализированный поиск проглоченных исключений, тихих фоллбэков и неверной пропагации ошибок.
14. **`code-simplifier` (`De-Sloppify`)** — удаление ИИ-мусора, мёртвого кода, лишних абстракций и избыточных проверок без изменения поведения.
15. **`refactor-cleaner`** — безопасный рефакторинг, устранение циклических зависимостей и очистка неиспользуемых экспортов.
16. **`build-error-resolver`** — быстрая диагностика и хирургическое устранение ошибок компиляции, бандлинга и разрешения модулей.
17. **`pr-test-analyzer`** — проверка качества самих тестов (ловит хрупкие моки и тесты, которые ничего не проверяют).
18. **`e2e-runner`** — разработка и прогон сквозных браузерных сценариев (Playwright / Cypress / DevTools MCP).
19. **`performance-optimizer`** — поиск узких мест CPU/памяти, утечек, лишних ререндеров, $N+1$ запросов и оптимизация размера бандла.

# 💾 Память (Unified Memory Vault), Самообучение (Homunculus Instincts v2.1) и Автономные Циклы

Этот справочник описывает архитектуру долговременной файловой памяти, систему накопления и эволюции атомарных инстинктов (`Homunculus v2.1`), стратегическое управление контекстным окном (`Strategic Compact`) и шаблоны декомпозиции крупных проектов (`Blueprint` + `Ralphinho RFC DAG`).

---

## 🧠 1. Система самообучения на атомарных инстинктах (`Homunculus Instincts v2.1`)

Обычные промты забываются после закрытия сессии. В `ecc-ultra-os` каждый исправленный недочёт, пользовательская поправка или выявленная особенность проекта превращается в **атомарный инстинкт** — компактное правило вида `Один Триггер -> Одно Действие` с весом уверенности (`confidence` от `0.30` до `0.95`).

### 1.1. Структура атомарного инстинкта
Инстинкты хранятся в JSON-реестре навыка (`resources/instincts.json`) или в локальном файле проекта (`.agents/instincts.json`):

```json
{
  "id": "always-verify-red-before-fix",
  "trigger": "При исправлении бага или добавлении новой бизнес-логики",
  "action": "Сначала написать воспроизводящий тест и убедиться, что он падает по ожидаемой причине (RED), прежде чем менять продакшен-код",
  "confidence": 0.95,
  "domain": "testing",
  "scope": "global",
  "evidence": [
    "Базовый инвариант ECC TDD Workflow",
    "Предотвращает ложноположительные тесты"
  ]
}
```

### 1.2. Шкала уверенности (`Confidence Scoring`) и Эволюция
- **`0.30 – 0.50` (Гипотеза / Наблюдение):** Замечено один раз в текущем проекте (`scope: "project"`). Применяется как мягкая рекомендация.
- **`0.60 – 0.75` (Устойчивый паттерн):** Подтверждено 2–3 раза или основано на прямой поправке пользователя.
- **`0.80 – 0.95` (Железный инстинкт):** Подтверждено многократно или критично для безопасности/архитектуры. Выполняется безусловно.
- **Правило промоушена (`Promote Project -> Global`):** Если проектный инстинкт оказывается полезным в 2+ разных репозиториях и не привязан к узкой бизнес-схеме одного проекта, он переводится в `scope: "global"`.
- **Правило кластеризации (`Evolve`):** Когда в одном домене накапливается 3–5 связанных инстинктов с `confidence >= 0.80`, они консолидируются в секцию проектного `AGENTS.md` / `GEMINI.md` или в новый специализированный референс.

## 🗄️ 2. Единое хранилище памяти (`Unified Memory Vault`)

Для того чтобы контекст не терялся между сессиями, субагентами и перезапусками, используется файловая память (никаких внешних БД не требуется — только читаемый Markdown и JSON в репозитории):

### 2.1. Три контура памяти
1. **Проектный оперативный контур (`AI_PROGRESS.md` или `.ecc/memory/project/`):**
   - Текущая фаза проекта, выполненные эпики и задачи из DAG, актуальные схемы БД, список открытых вопросов и блокеров.
2. **Архитектурный командный контур (`docs/adr/` или `.ecc/memory/team/`):**
   - Принятые архитектурные решения (**ADR — Architecture Decision Records**): контекст, рассмотренные альтернативы (вердикт `4-Voice Council`), выбранный путь и его последствия.
3. **Персональный контур оператора (`resources/instincts.json`):**
   - Предпочтения пользователя по стилю кода, языку общения, любимому стеку и оформлению интерфейсов.

### 2.2. Правила гигиены памяти
- **Сначала поиск, потом запись (`Recall Before Write`):** Перед созданием новой записи проверь, нет ли уже существующего документа, чтобы обновить его, а не плодить противоречивые копии.
- **Факты отдельно от намерений:** Всегда чётко помечай, что **уже реализовано и проверено тестами**, а что **запланировано на следующий шаг**.
- **Никаких секретов:** В файлы памяти категорически запрещено сохранять пароли, приватные ключи, `.env`-значения и персональные данные.

## 📉 3. Стратегическое управление контекстом (`Strategic Compaction Guide`)

Качество рассуждений любой модели падает в последних 20% контекстного окна из-за накопления «мусорного шума» (длинных логов, прочитанных файлов и промежуточных гипотез).

| Переход между фазами | Рекомендация по контексту | Что обязательно записать на диск ДО очистки |
| :--- | :---: | :--- |
| **Исследование $\rightarrow$ Планирование** | ✅ Отличная точка для `/compact` | Выжимку найденных файлов, сигнатур и ограничений в план (`*.plan.md` / `AI_PROGRESS.md`) |
| **Планирование $\rightarrow$ Реализация** | ✅ Идеальная точка для `/compact` | Полный утверждённый DAG / Blueprint с критериями приёмки на диск |
| **Отладка сложного бага $\rightarrow$ Новая фича** | ✅ Обязательно очистить трейсы | Причину бага, сделанный коммит-фикс и новый инстинкт в `instincts.json` |
| **Завершение спринта / эпика $\rightarrow$ Следующий эпик** | ✅ Отличная точка для `/compact` | Обновлённый статус в `AI_PROGRESS.md` и блок `Cold-Start Handoff` |
| **В середине написания связанного модуля** | ❌ НЕ сжимать контекст | Дождись прохождения тестов (`GREEN`) и коммита текущего среза |

## 📐 4. Шаблоны декомпозиции крупных задач (`Blueprint` & `Ralphinho RFC DAG`)

### 4.1. Шаблон `Blueprint` (Самодостаточный план для многошаговой разработки)
Каждый шаг плана обязан содержать **Cold-Start Context Brief**, чтобы любой агент мог выполнить этот шаг с нуля, даже не читая предыдущую переписку:

```markdown
# Blueprint: [Название фичи или миграции]

## Инварианты проекта (Не должны нарушаться ни на одном шаге)
- Сборка `npm run build` и типизация `tsc --noEmit` проходят с 0 ошибок после каждого шага.
- Обратная совместимость API сохраняется до финального шага очистки.

---

### Шаг 1: [Краткое название среза — размер 1 атомарного коммита/PR]
- **Зависимости (`depends_on`):** `none` (может выполняться сразу)
- **Уровень риска и модель:** `Low` | `Standard`
- **Cold-Start Context Brief:** [Какие файлы прочитать, какие типы и таблицы задействованы]
- **Затрагиваемые файлы:** `src/modules/auth/...`, `tests/auth/...`
- **Задачи (TDD):**
  1. Написать тест в `tests/...` (проверить `RED`).
  2. Реализовать логику в `src/...` (проверить `GREEN`).
- **Команда верификации:** `npm test -- tests/auth`
- **План отката (`Rollback`):** `git checkout -- src/modules/auth tests/auth`
```

### 4.2. Шаблон `Ralphinho RFC Pipeline` (Параллельный DAG для масштабных систем `T4`)
Когда проект или RFC слишком велик для одного прохода, разбей его на ациклический граф (`DAG`) независимых рабочих юнитов:

```text
[Unit 1: Core Schema & Types]
       ├──> [Unit 2A: Auth & RBAC Service] (Параллельная ветка 1)
       ├──> [Unit 2B: Billing & Webhooks]  (Параллельная ветка 2)
       └──> [Unit 2C: Analytics Pipeline]  (Параллельная ветка 3)
                   │
                   ▼
       [Unit 3: API Gateway & UI Integration (Merge Queue)]
                   │
                   ▼
       [Unit 4: E2E Playwright Suite & Final 6-Phase Verification]
```

**Правила очереди слияния (`Merge Queue Rules`):**
1. Ни один зависимый юнит не начинает финальную интеграцию, пока родительский юнит не прошёл локальную верификацию.
2. Независимые ветки (`2A`, `2B`, `2C`) не должны редактировать одни и те же строки одних и тех же файлов без явно согласованного интерфейса из `Unit 1`.
3. Если юнит застрял более чем на 3 попытках исправления сборки — изолируй проблему, сузь область юнита и перестрой проблемный узел графа.
